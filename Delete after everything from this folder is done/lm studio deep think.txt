Toto je podľa mňa najdôležitejší metodický problém verejnej verzie.

Takýto údaj nie je nezávislé meranie TTFT. Automaticky koreluje s celkovým časom, takže môže započítať tú istú výhodu konfigurácie dvakrát:



nižší total time
→ nižší estimated TTFT
→ lepšie performance skóre z dvoch metrík
Odporúčaná implementácia:



request_started = time.perf_counter()
first_token_at = None
last_token_at = None
 
async for event in stream:
    now = time.perf_counter()
 
    if event_contains_first_text_token(event):
        if first_token_at is None:
            first_token_at = now
 
    if event_contains_generated_text(event):
        last_token_at = now
 
ttft_s = first_token_at - request_started
generation_s = last_token_at - first_token_at
Po zavedení reálneho TTFT by som odstránil estimated_ttft zo scoringu alebo ho ponechal iba pri runtimoch, ktoré streaming timestamp neposkytnú, s explicitným príznakom:



ttft_source: Literal[

    "server_reported",

    "unavailable"

5. Requested config verzus applied config
V dokumentácii vidím capability discovery a ukladanie benchmark parametrov, ale pri každom výsledku potrebuješ samostatne ukladať:



requested_load_config
applied_load_config
ignored_parameters
modified_parameters
unsupported_parameters
Porovnanie:



def compare_configs(requested, applied):
    ignored = {}
    modified = {}
 
    for key, wanted in requested.items():
        if key not in applied:
            ignored[key] = wanted
        elif applied[key] != wanted:
            modified[key] = {
                "requested": wanted,
                "applied": applied[key],
            }
 
    return ignored, modified
Inak môže optimizer „otestovať“ päť rôznych konfigurácií, ktoré LM Studio interne načíta úplne rovnako.

4. Správne hľadanie maximálneho kontextu
Súhlasím, iba powers-of-two sú príliš hrubé. Ak 64K prejde a 128K zlyhá, optimom môže byť 76K, 91K alebo 112K.

Krok D: neplň celý kontext pri každom pokuse
Tu sa dá ušetriť najviac času.

Load-fit test
Najprv iba:

Toto zisťuje, či runtime alokáciu fyzicky zvládne.

Context-fill test
Až pre kandidátov blízko hranice:

potom 50 %,
potom 75 %,
potom 90 až 95 % okna.
Pre maximálny context report musí prejsť minimálne 90 % zaplnenie. Samotné načítanie 128K kontextu nedokazuje, že model zvládne spracovať 128K prompt.

Krok E: tvoj limit pod 1 tok/s
To je rozumná používateľská politika:



decode_tps < 1.0 = TOO_SLOW
Ale nedávaj to do rovnakého statusu ako OOM.

Použi:



PASS

FAIL_TIMEOUT
FAIL_CRASH
FAIL_CONTEXT_OVERFLOW
FAIL_QUALITY

Pri FAIL_TOO_SLOW zapíš:



{
  "threshold_tps": 1.0,
  "observed_tps": 0.83,
  "context_length": 76288,
  "fill_ratio": 0.9,
  "prompt_tokens": 68659,
  "output_tokens": 64

Krok F: hysteréza pri hranici
Ak nameriaš 0,98 tok/s, nemalo by to okamžite zlyhať kvôli šumu.

Navrhujem:



PASS: median >= 1.05 tok/s
BORDERLINE: 0.95 až 1.05 tok/s
FAIL: median < 0.95 tok/s
Borderline test zopakuj päťkrát a rozhodni podľa mediánu a variability.

To je moje návrhové pravidlo, nie pravidlo LM Studio.
